# Сервер «Первооткрытия» — Алхимическая Петля

Простой сервер на Python + FastAPI + SQLite для регистрации новых веществ, получаемых в игре путём варки неизвестных пар.

## Установка

```bash
cd server
pip install -r requirements.txt
```

## Запуск

```bash
# Из корня проекта
uvicorn server:app --host 0.0.0.0 --port 8080 --reload
```

Или из папки server:
```bash
cd server
uvicorn server:app --host 0.0.0.0 --port 8080 --reload
```

По умолчанию сервер слушает порт 8080.

## Базовый URL

`http://localhost:8080/api`

## API endpoints

### GET /api/health

Проверка доступности сервера.

**Ответ:**
```json
{"ok": true, "version": "1.0.0"}
```

### POST /api/brew-check

Проверка пары на кандидатура.

**Тело:**
```json
{"a": "fire", "b": "water", "nick": "Иван", "device_id": "device-123"}
```

**Успех 200:**
```json
{
  "ok": true,
  "pair_key": "fire|water",
  "found": false,
  "pending": false,
  "message": "Пара — кандидат на открытие"
}
```

### POST /api/discover

Регистрация нового первооткрытия (идемпотентно).

**Тело:**
```json
{"a": "fire", "b": "stone", "nick": "Иван", "device_id": "device-123"}
```

**Успех 201 (новое открытие):**
```json
{
  "ok": true,
  "discovery": {
    "id": 42,
    "slug": "pyroplit",
    "name": "Пироplit",
    "color": "#a87b3a",
    "layer": 2,
    "category": "огонь",
    "pair_key": "fire|stone",
    "a": "fire",
    "b": "stone",
    "author": "Иван",
    "seq": 1,
    "created_at": "2024-03-15T12:34:56"
  },
  "message": "ПЕРВООТКРЫТИЕ: Пироplit автор — Иван!"
}
```

### GET /api/world?page=1&per_page=50

Все известные элементы с пагинацией.

**Ответ:**
```json
{
  "ok": true,
  "elements": [
    {"id":1,"slug":"fire","name":"Огонь","color":"#ff936b","layer":0,"category":"огонь"},
    ...
  ],
  "page": 1,
  "per_page": 50,
  "total": 54
}
```

### GET /api/hall-of-fame

Топ-10 открытий.

**Ответ:**
```json
{
  "ok": true,
  "hall": [
    {"rank":1,"nick":"Анна","count":5,"updated_at":"2024-03-15T12:00:00"},
    ...
  ]
}
```

## Живой мир (лента + гонка)

- **`GET /api/events?limit=12`** — лента последних первооткрытий мира: кто, что,
  из какой пары и сколько минут назад (`world_events`).
- **`GET /api/challenge`** — ежедневная цель-гонка: детерминированный целевой
  ингредиент дня (`challenges`), подсказка «Вещество, рождённое из „X"»,
  победитель и счётчик открытий дня.
- При `discover` с новым результатом: событие пишется в ленту; если один из
  родителей — целевой ингредиент дня и цель ещё открыта — первый игрок
  объявляется победителем (поле `challenge` в ответе). БД — источник истины:
  победитель фиксируется, повторно выиграть нельзя.

## Профиль игрока (имя + аватар)

- **`GET /api/me?device_id=`** — ник и процедурный аватар игрока.
- **`POST /api/me`** `{device_id, nick}` — установить уникальное имя: нормализация
  (2–24 символа, буквы/цифры/пробел/дефис, спецсимволы отбрасываются), запись в
  `players`, возврат аватара.
- **Аватар** — детерминирован из ника (`avatar_for(seed)`): sha256 → цвет фона и
  акцента из палитры, индекс символа 0..11, флаг кольца. Клиент
  (`game/avatar.gd`) реализует тот же алгоритм — аватары всегда совпадают.
- Аватары включены в ответы: `discover` (`discovery.avatar`), `events`
  (`avatar`), `hall-of-fame` (`avatar`), `world` (`avatar` автора), `challenge`
  (`winner_avatar`).

## Архитектура

### Стартовый граф

Сервер при старте загружает полный локальный граф игры из `seed.py` —
**57 веществ / 53 рецепта** (имена, цвета, слои, категории, glyph, описание).
Известные пары отдаются как есть, генерация запускается только для действительно
неизвестных пар. **БД — источник истины**: любое решение (создан элемент или
отказ) фиксируется один раз, повторный запрос той же пары LLM не вызывает.

### Гибридная генерация (LLM + фоллбэк)

Для неизвестной пары сервер спрашивает языковую модель — каков **самый
очевидный результат, непосредственно объяснимый ОБОИМИ веществами** (не
произвольная ассоциация). LLM отвечает только `{"combinable": true, "name": …}`
или `{"combinable": false}`; категорию, glyph и описание назначает сервер.

Механизмы результата (в промпте): `construction` (части→целое),
`group` (пара/группа), `mixture` (смесь), `interaction` (физическое
взаимодействие) и `reference` — **отсылки к мемам, играм, поп-культуре и музыке
разрешены, но сильно оправданы**: оба вещества должны напрямую и без натяжек
указывать на отсылку, а результат — её каноническое имя (напр. Кольцо+Магия →
Кольцо Всевластия). Натянутая отсылка (Птица+Пепел → Феникс) — `combinable:false`.
Возможные исходы:

1. **Создано** (`status="created"`, `gen_method="llm"`) — модель вернула имя;
   цвет вычисляется детерминированной смесью, слой = max+1, категория/glyph/описание —
   от сервера.
2. **Туман** (`status="not_combinable"`) — модель решила, что очевидного результата
   нет (или все кандидаты отклонены семантическим валидатором). Пара сохраняется в
   `rejected_pairs` и дальше всегда отвечает «туманом», LLM больше не вызывается.
3. **Недоступна** — провайдер `off` (или LLM без ключа при явном выборе): сервер
   не выдумывает имя и не фиксирует решение — отвечает `status="unavailable"`, пара
   остаётся кандидатом и будет сгенерирована, когда провайдер настроится.

По умолчанию включён **локальный генератор** (`LLM_PROVIDER=local`): курируемая
таблица `LOCAL_OBVIOUS` в `gen_llm.py` детерминированно отвечает на очевидные,
непосредственно объяснимые ОБОИМИ веществами пары (Вода+Вода→Озеро, Металл+Уголь→
Сталь, Огонь+Лес→Пожар…), а всё остальное — «туман». Поэтому новые пары создаются
сразу, без сети и ключа; для полной LLM-генерации задайте ключ провайдера.

Качество обеспечивают: позитивные и негативные few-shot в system-промпте
(«Кирпич+Кирпич→Стена» VALID, «Стена+Стена→Дом» VALID, «Камень+Камень→Кот»
INVALID, «Стена+Стена→Ртуть» INVALID), требование внутренней самопроверки,
раздельные retry (форматная ошибка → строгий JSON; семантическая ошибка →
«выбери другой, более очевидный результат») до 3 попыток, отдельный этап
семантической проверки (детерминированные guardrail'ы + строгий LLM-валидатор,
который так же строго проверяет оправданность отсылок).

Ротация моделей размазывает бесплатные лимиты (у каждой `:free`-модели
OpenRouter свои ~50–1000 запросов/день).

### Experiment Bench и квоты

Клиент может помечать явный запрос из Experiment Bench полем `experiment` в
`/api/brew-check` и `/api/discover` — но только для UX/аналитики: на квоту оно
НЕ влияет. Известные `recipes`, `rejected_pairs` и локальный/curated provider
возвращаются без внешнего LLM-вызова и не расходуют quota. Для новой пары
сервер резервирует бюджет по ФАКТУ обращения к генератору (внутри
`_generate_for_pair`, ключ — `device_id`) в SQLite-таблицах `experiment_limits`
(устройство + день) и `experiment_global_limits` (весь сервер + день). При
`unavailable` резерв возвращается (квота сгорает только на реальные вызовы),
а пару можно повторить после восстановления провайдера.

Значения по умолчанию: 200 внешних попыток на устройство в сутки, cooldown 5
секунд и 10000 попыток на весь сервер в сутки.

Письма Светика (`/api/letter/today`) имеют ОТДЕЛЬНЫЙ дневной бюджет LLM-вызовов
в таблицах `letter_limits` / `letter_global_limits`: по умолчанию 3 генерации
намёка на устройство в сутки, cooldown 30 секунд и 3000 на весь сервер. При
исчерпании письмо просто не генерируется (ответ остаётся корректным). Страница
Атласа (`/api/atlas/today`) — третий LLM-оракул — имеет свой мировой бюджет в
таблицах `atlas_limits` / `atlas_global_limits` (без device-ключа, по
фиксированному ключу `""`): по умолчанию 10 генераций в сутки на весь сервер,
cooldown 60 секунд; при `LLMError` или пустой загадке резерв возвращается. Все
лимиты настраиваются окружением: `ALCHEMY_EXPERIMENT_DAILY_LIMIT`,
`ALCHEMY_EXPERIMENT_COOLDOWN_SEC`, `ALCHEMY_EXPERIMENT_GLOBAL_DAILY_LIMIT`,
`ALCHEMY_LETTER_DAILY_LIMIT`, `ALCHEMY_LETTER_COOLDOWN_SEC`,
`ALCHEMY_LETTER_GLOBAL_DAILY_LIMIT`, `ALCHEMY_ATLAS_DAILY_LIMIT`,
`ALCHEMY_ATLAS_COOLDOWN_SEC`.

### Настройка генерации (env)

Проще всего — положить ключ в файл **`.env`** рядом с `server.py` (смотрите
`.env.example`): сервер читает его при старте. Реальное окружение (export в
шелле, systemd `Environment=`) имеет приоритет над файлом.

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `LLM_PROVIDER` | `local` | `local` (по умолчанию) \| `openrouter` \| `openai_compatible` \| `mock` \| `off` |
| `OPENROUTER_API_KEY` (или `LLM_API_KEY`) | — | ключ API |
| `LLM_MODELS` | 6 бесплатных моделей | список через запятую (ротация по кругу) |
| `LLM_BASE_URL` | — | для `openai_compatible`: Groq `https://api.groq.com/openai/v1`, Together `https://api.together.xyz/v1`, Mistral `https://api.mistral.ai/v1`, Fireworks, Ollama и т.п. |
| `LLM_TIMEOUT` | `30` | таймаут одного запроса, сек |
| `LLM_MAX_ATTEMPTS` | `3` | попыток генерации на пару; меньше = быстрее отказ при недоступной LLM |
| `ALCHEMY_EXPERIMENT_COOLDOWN_SEC` | `5` | cooldown внешнего Experiment на device |
| `ALCHEMY_EXPERIMENT_DAILY_LIMIT` | `200` | внешний LLM budget на device/day |
| `ALCHEMY_EXPERIMENT_GLOBAL_DAILY_LIMIT` | `10000` | общий внешний LLM budget/day |
| `ALCHEMY_DEBUG` | — | `1` — подробные логи LLM-слоя |
| `ALCHEMY_LOG_RAW` | — | `1` — писать сырые ответы моделей в лог |
| — | — | пулов имён больше нет: имя даёт только LLM |

Тот же пример через `.env` (файл `server/.env`):
```dotenv
LLM_PROVIDER=openrouter
OPENROUTER_API_KEY=sk-or-v1-...
LLM_MODELS=google/gemma-4-31b-it:free,nvidia/nemotron-3-super-120b-a12b:free
```
Или в терминале (export действует до закрытия сессии):
```bash
export LLM_PROVIDER=openrouter
export OPENROUTER_API_KEY=sk-or-v1-...
export LLM_MODELS="google/gemma-4-31b-it:free,nvidia/nemotron-3-super-120b-a12b:free"
uvicorn server:app --host 0.0.0.0 --port 8080
```

Пример (Groq как openai-совместимый провайдер):
```bash
export LLM_PROVIDER=openai_compatible
export LLM_BASE_URL=https://api.groq.com/openai/v1
export LLM_API_KEY=gsk_...

```

### Диагностика, когда пара «не оценивается»

Если в игре «мир сейчас не может оценить эту пару», смотрите лог сервера. Каждая
попытка генерации пишется с указанием модели, причины и времени. При ошибке
формата в лог пишется и **сырой ответ модели** — видно, что именно она вернула:

```
INFO  alchemy.llm: пара «Пыль» + «Небо»: генерирую (провайдер openrouter, модели: ...)
WARN  alchemy.llm: попытка 1/3: google/gemma-4-31b-it:free → HTTP 401: 401 User not found. (за 0.2s)
ERROR alchemy.llm: пара «Пыль» + «Небо»: генерация не удалась (0.2s): ...
WARN  alchemy: пара dust+sky: LLM недоступна → unavailable (...)
```

Частые причины и что делать:

- **`401 User not found` / `401 Invalid credentials`** — ключ неверный или не
  активирован. Проверьте ключ на https://openrouter.ai/settings/keys.
- **`402`/`429` (кредиты/лимит)** — на free-моделях лимиты ~50 запросов/день на
  модель; ротация `LLM_MODELS` размазывает их. Пополните баланс или смените модели.
- **`404 ... model not found`** — список free-моделей устарел (они часто
  меняются). Обновите `DEFAULT_MODELS` в `gen_llm.py` по
  https://openrouter.ai/api/v1/models (фильтр `:free`) или задайте свои `LLM_MODELS`.
- **`сеть: Timeout`** — модель не отвечает: увеличьте `LLM_TIMEOUT` или
  уменьшите `LLM_MAX_ATTEMPTS`.
- **`ответ не по формату`** — модель ответила (HTTP 200), но не JSON: ниже в
  логе будет `сырой ответ модели`. Это не ошибка пары: пара **не** помечается
  «не сочетается», а остаётся кандидатом (статус `unavailable`) и перегенерируется
  позже. Если так происходит постоянно — модель слишком «болтливая»: смените
  `LLM_MODELS` на более послушную или не-reasoning модель.

Технический сбой ≠ «не сочетается»: пара помечается отказом только если модель
явно вернула `{"combinable": false}`. Сеть/429/битый формат → `unavailable`,
решение не фиксируется, пара генерируется повторно.

`ALCHEMY_DEBUG=1` включает DEBUG-логи, `ALCHEMY_LOG_RAW=1` — сырые ответы модели.

Промпт модели требует строгий JSON: `{"combinable": true, "name": "…"}` или
`{"combinable": false}`. Модель выбирает самый очевидный результат, объяснимый
ОБОИМИ элементами (few-shot + самопроверка + строгий семантический валидатор +
retry с обратной связью до 3 попыток). Категорию, glyph и описание назначает
сервер.

### Недоступность модели

Пулов имён больше нет: если модель недоступна (нет ключа/сеть/лимиты), сервер
не выдумывает имя и не фиксирует решение — отвечает `status="unavailable"`,
пара остаётся кандидатом и будет сгенерирована, когда модель вернётся.

Категория результата — категория более «глубокого» родителя (при равных
слоях — второго в каноническом порядке).

### Генерация цвета

Взвешенное усреднение цветов родителей с весом `1 + layer/10`. Если результат
ближе 32 единиц RGB к родителю или совпадает с существующим цветом —
детерминированный сдвиг (LCG по hash(pair_key)).

### Блокировка пар (race-condition)

Блокировку берёт только `/api/discover` (brew-check — чисто читающий):

1. `INSERT INTO pending_pairs (pair_key, state, lock_ts, owner) VALUES (...) ON CONFLICT(pair_key) DO UPDATE SET state='locked', ...`
2. Если пара уже залочена другим запросом (state='locked' и свежий lock_ts) — `409 Conflict`
3. После генерации — `UPDATE pending_pairs SET state='resolved'`

### Авторство

- `players` таблица: nick, device_id UNIQUE; игрок авторегистрируется при
  любом запросе (brew-check / discover), поэтому сразу попадает в зал славы
- `elements.author` → nick игрока (у стартовых веществ — NULL)
- `recipes.discoverer` → nick игрока (у стартовых рецептов — NULL)
- `created_at` → timestamp

## Настройка

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `ALCHEMY_DB_PATH` / `DB_PATH` | папка данных пользователя (см. ниже) | Путь к SQLite-файлу (перекрывает дефолт) |
| `SERVER_URL` | `http://localhost:8080` | URL сервера (информационный) |
| `DAY_TZ_OFFSET` | `0` (UTC) | Фиксированное смещение «суток» сервера, `[+-]HH[:MM]` (напр. `+03:00` — сутки по МСК) |

### Единая временная шкала (T06)

Все «сутки» сервера (цель дня, письма, Атлас, жила/ярмарка, лента
`today_events`, дневные квоты LLM) живут в ОДНОЙ шкале: текущий момент UTC,
сдвинутый на `DAY_TZ_OFFSET`. Серверные `created_at`/`first_at` и дневные
ключи пишет только этот хелпер (`_now_dt`/`_today`/`_now_iso` в `server.py`);
SQLite `date('now')`/`datetime('now')` в запросах из Python больше не
используются — дата считается в Python и передаётся параметром. Дефолты
схемы `DEFAULT (datetime('now'))` — UTC, но это только audit-колонки, ни с
какими дневными ключами не сравнивающиеся. Эпохи `time.time()` (лок пар,
cooldown квот) от таймзоны не зависят. Невалидный `DAY_TZ_OFFSET` — падение
на старте. Старые строки (писавшиеся в смешанных шкалах) не мигрируются:
с момента деплоя записи равномерны, а дневные ключи переворачиваются один раз.

### Где хранится база данных

По умолчанию БД лежит **в папке данных пользователя** (appdata), а не рядом с кодом,
чтобы не теряться при обновлении/переезде репозитория:

- Linux: `$XDG_DATA_HOME/AlchemistsLoop/discoveries.db` (или `~/.local/share/AlchemistsLoop/discoveries.db`)
- macOS: `~/Library/Application Support/AlchemistsLoop/discoveries.db`
- Windows: `%APPDATA%\AlchemistsLoop\discoveries.db`

Точный путь пишется в лог при старте. При первом запуске, если рядом со скриптом
лежит старая БД (`server/discoveries.db`), а в пользовательской папке её ещё нет —
файл автоматически переносится туда (копия + оригинал сохраняется).

Переопределить путь можно переменной `ALCHEMY_DB_PATH` (или устаревшей `DB_PATH`):
оба варианта имеют приоритет над дефолтной папкой.

## Экспорт и удаление пользовательских данных (v0.2)

- `GET /api/account/export?device_id=...` — возвращает профиль, домик,
  первооткрытия и отголоски устройства перед удалением.
- `DELETE /api/account?device_id=...` — удаляет профиль и персональные таблицы
  (`echoes`, письма, очки целей, атлас, недельные вклады). Опубликованные в
  общем мире элементы не удаляются: их авторство и записи ленты становятся
  «Анонимный алхимик», чтобы не сломать рецепты остальных игроков.

Клиентская кнопка удаления сначала удаляет локальный прогресс и отправляет этот
запрос, если сервер доступен. Ссылка на политику конфиденциальности и контакт
