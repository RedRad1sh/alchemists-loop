# Первооткрытия и серверный слой — спецификация

## Часть А. Механика «пары-кандидаты»

### A.1. Когда локальная варка неизвестной пары становится кандидатом

Кандидатом на первооткрытие становится результат `_brew()`, удовлетворяющий трём условиям:

1. **Оба ингредиента открыты игроком.**  
   Игра хранит `known_recipes` (набор `pair_key → true`). Если пара `(a, b)` уже есть в `known_recipes` — это обычный успех/неудача, не кандидат.  
   Кандидат — только когда `_find_recipe(a, b)` возвращает пустое значение **и** оба ингредиента есть в инвентаре (игра их знает, т.е. `inventory[a] > 0`, `inventory[b] > 0`).

2. **Пара X+X допустима.**  
   Пара вида `(a, a)` (один ингредиент в обе лунки) — валидный кандидат. В текущей локальной механике `_has_ingredients(a, b)` проверяет наличие **по 1 шт.** каждого; при X+X нужно проверять наличие ≥2 шт. одного ингредиента. Клиент делает это преобразование перед отправкой.

3. **Клиент отличает «просто неудачу» от кандидата без спама сервера.**  
   Механизм «шанс тумана»:
   - При варке неизвестной пары клиент проверяет **5% вероятность** на клиенте перед отправкой.
   - Если шанс не срабатывает — пара трактуется как кандидат, клиент отправляет `brew-check`.
   - Если шанс срабатывает — клиент ведёт себя как сейчас: «Туман рассеялся…», возврат 1 эфира, **нет** запроса к серверу.
   - Дополнительно: клиент запоминает `last_candidate_time` для пары; повторный кандидат от той же пары игрока не отправляется чаще раза в 60 сек. Это защищает от спам-нумера при автоварке.

**Аргументация выбора:** сервер не может дифференцировать «неудачу» и «кандидат» без подсказки от клиента. Клиент-гейшанс 5% балансирует между: (а) не превращением каждой неудачной варки в сетевой запрос (игрушка однопользовательская, кандидаты редки), (б) не пропуском редких реальных кандидатов. При 1000 варок/сессию ожидается ~50 кандидатов — адекватно.

### A.2. Жизненный цикл

```
Клиент: _brew() → неудача + оба ингредиента известны + 5% шанс + 60c cooldown → 
  [POST /api/brew-check {"a":"fire","b":"water","nick":"Варг","device_id":"..."}]

Сервер:
  1. pair_key = canonical(a,b)   # нормализованный ключ "fire|water"
  2. Авторегистрация игрока (players); если pair_key уже в recipes → {"found": true, "out": {...}, "author": {...}}
  3. Если pair_key в rejected_pairs → {"found": false, "status": "not_combinable"}
  4. Если нет → блокировка пары (pending_pairs) и генерация (см. A.3):
       - LLM-модель решает: очевидный результат → имя; бессмысленная пара → «туман» (rejected_pairs)
       - категорию определяет СЕРВЕР; glyph, описание и tag модель может предложить — сервер берёт их только валидными, иначе фолбэк
       - LLM недоступна → статус unavailable, решение НЕ фиксируется (пара остаётся кандидатом)
       - цвет (детермин. смесь + проверка различимости), слой = max(layer_a, layer_b)+1
     → INSERT в elements, INSERT в recipes (pair_key → новый out_id) или INSERT в rejected_pairs
     → вернуть {"found": false, "status": "created"|"not_combinable", "discovery": {...}}

Клиент:
  - Если found==true: показать «этот рецепт уже открыт X» (опционально)
  - Если status=="created": показать карточку «ПЕРВООТКРЫТИЕ: [имя] автор: [ник]», 
    добавить элемент в локальный словарь ITEMS, добавить рецепт в local_recipes.json,
    обновить инвентарь
  - Если status=="not_combinable": «Туман рассеялся…» (элемент не создан)
  - При таймауте/ошибке сети: вести себя как сейчас — «Туман рассеялся…» + возврат 1 эфира
```

### A.3. Генерация вещества

**Стартовый граф.** Сервер при старте загружает полный локальный граф игры
(`seed.py`: **57 веществ / 53 рецепта** с именами, цветами, слоями, категориями и семантическим `glyph`).
Поэтому `/api/world` сразу возвращает реальную известную вселенную, а пары,
которые игра уже знает, отдаются как есть (идентичность) **без генерации** —
новые элементы создаются только для действительно неизвестных пар.

**Имя (основной путь — LLM).** Неизвестная пара отправляется языковой модели
(`gen_llm.py`, провайдеры OpenRouter / любой openai-совместимый эндпоинт,
ротация бесплатных моделей). Модель должна выбрать **самый очевидный результат,
непосредственно объяснимый ОБОИМИ входными элементами**, а не произвольную
ассоциацию (приоритет: прямой физический/природный результат → очевидное
построение → очевидное взаимодействие → сильная культурная ассоциация; натянутые
цепочки запрещены). Модель возвращает строгий JSON:

`{"combinable": true, "name": "Дом"}` либо `{"combinable": false}` — если у пары
нет очевидного результата (тогда пара пишется в `rejected_pairs` и навсегда
остаётся «туманом»). Категорию определяет СЕРВЕР, а `glyph`, описание и `tag`
модель может предложить — сервер берёт их только прошедшими валидацию, иначе
подставляет детерминированный фолбэк.

В system-промпте — позитивные и негативные few-shot («Кирпич+Кирпич→Стена»
VALID, «Стена+Стена→Дом» VALID, «Камень+Камень→Кот» INVALID, «Стена+Стена→Ртуть»
INVALID) и требование внутренней самопроверки (несколько кандидатов → вклад обоих
элементов → отброс односторонних/длинных цепочек → выбор самого очевидного →
иначе `combinable:false`). Наружу — только финальный JSON.

**Retry (раздельные каналы).** До 3 попыток на пару: форматная ошибка → повтор с
требованием строгого JSON; семантическая ошибка (кандидат отклонён отдельным
этапом проверки) → повтор с инструкцией «предыдущий кандидат не подходит, выбери
более очевидный или `combinable:false`». Исход после попыток различается:
отказ модели (явный `combinable:false`, либо невалидное/пустое имя от генератора)
фиксируется навсегда — пара пишется в `rejected_pairs`; техническая
недоступность модели (`LLMError`) даёт `status="unavailable"`, списанную квоту
сервер возвращает и решение НЕ фиксируется — пара остаётся кандидатом
(см. «Недоступность модели» ниже). Семантическая проверка — отдельный этап:
детерминированные guardrail'ы (имя ≠ ингредиенту, не склейка имён) + строгий
LLM-валидатор (`validate_result` при этом проверяет только технику: JSON,
`combinable`, русское имя без цифр/латиницы/дефисов, длину).

**Недоступность модели.** Если модель недоступна (нет ключа/сеть/лимиты),
сервер НЕ выдумывает имя (никаких «пулов» произвольных существительных) и НЕ
фиксирует решение: пара отвечает `status="unavailable"` и остаётся кандидатом —
её можно сгенерировать позже, когда модель вернётся. Имена результатам даёт
только LLM; готовый граф 57/53 покрывает игру локально.

**БД — источник истины.** Никаких ручных списков несочетаемых пар в
продакшен-логике нет (`DEFAULT_REJECT_PAIRS`/`MOCK_REJECT`/`REJECT_PAIRS` удалены).
Для каждой пары используется канонический ключ `min(slug1, slug2)|max(slug1, slug2)`:
запись в `recipes` → вернуть сохранённый результат; запись в `rejected_pairs` →
вернуть «туман»; иначе — вызвать LLM, проверить результат, сохранить решение
(элемент+рецепт или отказ) и больше его не пересчитывать. Повторный запрос той же
пары LLM не вызывает. Решение не зависит от доступности или выбора модели после
сохранения в БД.

**Слаг.** `slugify(имя)` → латиница, строчные (транслитерация й→y, ё→yo, ж→zh,
х→kh, ь/ъ→пусто). При коллизии слага — суффикс `-N`.

**Цвет.** Детерминированная взвешенная смесь:
```
R = round( (R_a*w_a + R_b*w_b) / (w_a + w_b) )   (аналогично G и B)
w = 1 + layer/10          # более глубокий элемент сильнее влияет на цвет
```
После смешивания — проверка **различимости**: если результат ближе 32 единиц
(Euclidean RGB) к любому из родителей или совпадает с уже существующим цветом,
применяется детерминированный сдвиг (LCG по `hash(pair_key)`), до 24 попыток.

**Слой.** `layer = max(layer_a, layer_b) + 1`. Базовые стихии (fire/water/earth/air) — слой 0.

**Категория.** Категория более «глубокого» родителя (у кого больше слой); при
равных слоях — категория второго родителя в каноническом порядке.

### A.4. Анти-коллизии и race condition

**Повторное открытие той же пары вторым игроком:**
- `recipes.pair_key` имеет UNIQUE-индекс. Второй запрос на `discover` той же пары проверяет существование записи → возвращает того же автора.  
- Дополнительно: если пара уже есть в `recipes`, `brew-check` тоже возвращает existing элемент без генерации.

**Race condition (два параллельных запроса на одну новую пару):**
- Решение: **серверная очередь по pair_key с блокировкой**.
- Реализация в SQLite (с UVicorn, single-threaded по умолчанию, но для безопасности):
  1. Таблица `pending_pairs(pair_key TEXT PRIMARY KEY, state TEXT, lock_ts REAL)` — запись с UNIQUE индексом.
  2. При запросе `discover` на новую пару: атомарный `INSERT OR IGNORE INTO pending_pairs (pair_key, state, lock_ts) VALUES (?, 'locked', ?)`.
  3. Если INSERT прошел (ни одна из параллельных транзакций не заняла ключ) — этот запрос владеет блокировкой, генерирует элемент.
  4. Если INSERT не прошел (найдена существующая запись с state='locked') → ждать (polling с 50мс backoff до 2 сек) или вернуть ошибку `409 Conflict` с сообщением «пара в обработке».
  5. После генерации/обнаружения: `UPDATE pending_pairs SET state='resolved', resolved_by=? WHERE pair_key=?`.
- Так как в рамках прототипа сервер однопоточный (uvicorn с 1 воркером), race-условия между запросами не возникают на уровне событийного цикла — но блокировка добавлена для корректности при горизонтальном масштабировании.

Альтернатива для production: Redis-блокировки / advisory locks в PostgreSQL.

### A.5. Авторство

- `players` таблица: `nick TEXT, device_id TEXT UNIQUE`. Уникальность по device_id гарантирует, что один клиент = один玩家记录.
- `elements.author → players.nick` (подписка, не внешний ключ — для гибкости).
- `recipes.discoverer → players.nick`.
- `created_at` = `CURRENT_TIMESTAMP`.
- `seq` — монотонный счётчик первооткрытий на сервере (для hall-of-fame).

## Часть Б. API-референс

Базовый URL: `http://<server>:8080/api`

### POST /api/brew-check

**Назначение:** проверить, является ли пара кандидатом на открытие, и если да — инициировать discover.

**Запрос:**
```json
{
  "a": "fire",
  "b": "water",
  "nick": "Иван",
  "device_id": "save-2024-03-15-1234"
}
```

**Успех 200:**
```json
{
  "ok": true,
  "pair_key": "fire|water",
  "found": false,
  "discovery": null,
  "pending": true,
  "message": "пара в обработке"
}
```
или (если пара уже известна):
```json
{
  "ok": true,
  "pair_key": "fire|water",
  "found": true,
  "out": {
    "id": 5,
    "slug": "steam",
    "name": "Пар",
    "color": "#c4cfe5",
    "layer": 1,
    "category": "воздух",
    "author": null,
    "created_at": null
  },
  "discoverer": {
    "nick": "Анна",
    "seq": 12
  },
  "pending": false,
  "message": "рецепт уже открыт"
}
```

**Ошибки:**
- `400 Bad Request` — недостаточно ингредиентов или невалидные id.
- `409 Conflict` — пара в обработке другим запросом (пolemia).
- `500` — внутренняя ошибка.

**cURL:**
```bash
curl -s -X POST http://localhost:8080/api/brew-check \
  -H 'Content-Type: application/json' \
  -d '{"a":"fire","b":"water","nick":"Иван","device_id":"abc"}'
```

### POST /api/discover

**Назначение:** атомарно зарегистрировать новое первооткрытие (идемпотентно по pair_key).

**Запрос:** аналогично brew-check.

**Успех 201 (новое открытие):**
```json
{
  "ok": true,
  "discovery": {
    "id": 42,
    "slug": "pyrolyt",
    "name": "Пиrolyт",
    "color": "#b48a44",
    "layer": 2,
    "category": "огонь",
    "pair_key": "fire|stone",
    "a": "fire",
    "b": "stone",
    "author": "Иван",
    "seq": 1,
    "created_at": "2024-03-15T12:34:56"
  }
}
```

**Успех 200 (идентификация — пара уже открыта):**
```json
{
  "ok": true,
  "already_known": true,
  "discovery": { ... },
  "message": "пара уже открыта [ник]"
}
```

**Ошибки:**
- `400` — валидация.
- `409` — пара в обработке.

**cURL:**
```bash
curl -s -X POST http://localhost:8080/api/discover \
  -H 'Content-Type: application/json' \
  -d '{"a":"fire","b":"water","nick":"Иван","device_id":"abc"}'
```

### GET /api/world

**Назначение:** получить все известные элементы для отображения на вкладке «Мир». Пагинация.

**Запрос:** `?page=1&per_page=50`

**Успех 200:**
```json
{
  "ok": true,
  "elements": [
    {"id":1,"slug":"fire","name":"Огонь","color":"#ff936b","layer":0,"category":"огонь"},
    ...
  ],
  "page": 1,
  "per_page": 50,
  "total": 100
}
```

**cURL:**
```bash
curl -s http://localhost:8080/api/world?page=1
```

### GET /api/hall-of-fame

**Назначение:** топ открытий по количеству.

**Успех 200:**
```json
{
  "ok": true,
  "hall": [
    {"rank":1,"nick":"Анна","count":42,"updated_at":"..."},
    {"rank":2,"nick":"Варг","count":38},
    ...
  ]
}
```

**cURL:**
```bash
curl -s http://localhost:8080/api/hall-of-fame
```

### GET /api/health

**Успех 200:**
```json
{"ok":true,"version":"1.0.0"}
```

## Критерии приёмки (чеклист)

- [ ] `pip install -r requirements.txt` → успех.
- [ ] `uvicorn server:app --host 0.0.0.0 --port 8080` → поднимается, `/api/health` отвечает.
- [ ] Два параллельных `discover` одной новой пары → один результат, один автор.
- [ ] Клиент без сети полностью повторяет текущий офлайн-геймплей (никаких зависаний UI).
- [ ] JSON-ответ `GET /api/world` ложится на сетку орбов вкладки «Мир» (поля name/color достаточно) и содержит стартовый граф 57/53.
- [ ] Известные пары из локальной игры возвращаются без генерации (identity).
- [ ] Новая пара создаётся через LLM (LLM решает сочетимость и имя, может предложить `glyph`/описание/`tag` — сервер берёт их только валидными, иначе фолбэк; категорию определяет сервер); при недоступности модели — `status="unavailable"`, решение не фиксируется, пара остаётся кандидатом.
- [ ] Бессмысленная пара (по решению модели) → `status="not_combinable"`, сохраняется в `rejected_pairs`, повторный запрос той же пары LLM не вызывает, и в `brew-check` отдаётся «туман».
- [ ] Кирпич+Кирпич → Стена и Стена+Стена → Дом работают стабильно; «Стена+Стена→Ртуть» и «Камень+Камень→Кот» не принимаются (few-shot + самопроверка + семантический валидатор + retry с обратной связью).
- [ ] Новые вещества получают осмысленные русские имена (без склейки морфем вида «под-мор-ь»).
- [ ] Pytest зелёный (корень `server/`).
- [ ] `GET /api/events` возвращает ленту первооткрытий (кто/что/из чего/когда); известные пары событий не создают.
- [ ] `GET /api/challenge` отдаёт детерминированную цель дня (целевой ингредиент + подсказка), `first_nick`, `completions`, `my_points`; день не «закрывается» глобально: `won` в поле `challenge` ответа `discover` — персональный (награда ровно один раз на устройство за день, повторные попадания в целевой ингредиент идут в очки дня без награды), глобально от дня фиксируется только первый справившийся `first_nick`; повторно выиграть нельзя.
- [ ] `GET/POST /api/me` — профиль игрока: ник нормализуется (2–24 символа, без спецсимволов), сохраняется за `device_id`, переименование не теряет устройство.
- [ ] Аватар детерминирован из ника и совпадает с клиентским (`game/avatar.gd`); аватары присутствуют в `discover`/`events`/`hall-of-fame`/`world`/`challenge`.
