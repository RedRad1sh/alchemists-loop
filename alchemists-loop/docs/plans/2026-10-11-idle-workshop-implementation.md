# Idle Workshop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` to implement this plan task-by-task. Steps use checkbox syntax. Delegate only bounded implementation; integration, investigation and review remain with the main agent unless explicitly requested otherwise.

**Goal:** Добавить мастерство за новые открытия и реальные операции длинных цепочек, материальное развитие Мастерской, независимые линии и полноценную офлайн-очередь.

**Architecture:** `Workshop` владеет прогрессом и заданиями; `WorkshopScheduler` последовательно коммитит операции независимых линий в общий инвентарь. Начисление мастерства находится в подтверждённых путях получения результата, а не в UI или завершении плана. Онлайн и офлайн используют один исполнитель времени/ресурсов.

**Tech Stack:** Godot 4.7.2, GDScript, существующие JSON-сейвы и Godot selftest; новые зависимости и серверные API не нужны.

**Spec:** `docs/plans/2026-10-11-idle-workshop-design.md` — утверждена, включая мастерство и сохранение оборудования через Перегонку.

## Global Constraints

- Все пути ниже относительно `alchemists-loop/`. Не читать `.env`, секреты, живую БД и реальные пользовательские сейвы.
- Не затрагивать чужие незакоммиченные ассеты/backup/БД. Сохранить согласованные багфиксы Аркана и Круга; CRLF существующих `.gd`.
- Рецепты остаются двухкомпонентными. Цены каталога сигилов и регенерация эфира не изменяются.
- Мастерство: `clamp(content_layer, 1, 6)` за каждый успешный небазовый выход после первого открытия Мастерской. За всю цепочку — сумма выполненных операций; никакого второго начисления за её завершение.
- Ранги: опыт `0/100/400/1000`, линии и ёмкость заданий `1/2/3/4`. Опыт не тратится.
- Переходы: `brick:20, metal:10, ether:120`; `glass:25, tool:10, ether:240`; `crystal:20, gold:10, ether:480`.
- Автономность: `60/120/240` офлайн-этапов на линию. Покупки: ранг ≥1, `glass:15, metal:10, ether:150`; ранг ≥2, `tool:15, crystal:10, ether:300`.
- Базовый этап линии `40 с`, существующие операции этапа `3/4/5`, офлайн-фактор `0.5`, окно `8 ч`, нижняя граница офлайн `60 с`.
- Архивная печать `Core.mastery_rank` не является мастерством Мастерской. Чертёж `−10%` и сигильный milestone 13 `×2` сохраняют действие.
- Круг: пять успешных синтезов, цель и заказы обязательны, награда `75` один раз в день.
- Родник/эффекты хроматик/повторяемый endgame — отдельные этапы. Их функциональность не заявлять выполненной этим планом.
- Не устанавливать/обновлять Python или зависимости. Перед серверными тестами спросить статус обновления; при текущих блокерах сообщить «не запущены».
- Не коммитить, не stage, не push. Вместо commit-шагов — ревью diff и фактические проверки.

## Review Focus

1. Новое/повторное онлайн-открытие, старый ответ после Перегонки, повтор доставки: мастерство только за собственный подтверждённый выход (Task 1).
2. Одинаковая цель двух линий, общий последний реагент, `a == b`: не удвоить расход/выход и не превысить поддерживаемый запас (Tasks 3–4).
3. Глубина-сентинел циклического/неизвестного графа и повреждённые числа сейва: не превращать невалидные данные в максимум мастерства (Tasks 1–2).
4. Загрузка будущей версии, обратные часы, перезапуск на середине цепочки: сохранить данные, не дублировать выдачу (Task 5).
5. Ручная варка, покупка оборудования и отложенный расход Аркана между этапами: проверить фактические ресурсы при коммите (Tasks 2–4).

## Task 3: Явный контекст операции и защита общего расхода

**Files:** `core.gd`, узкие проверки входа в покупки `workshop.gd`/`sigil_ui.gd`, `suite_workshop_scheduler.gd`, selftest.

**Consumes:** Task 1 `on_synthesis`; существующие `_pair_cost`, `_production_pair_block`, `_has_ingredients` и fail-closed дебет.

**Produces:** совместимая сигнатура `Core._commit_brew(a: String, b: String, context: Dictionary = {}) -> Dictionary`; `Core._resource_mutation_allowed() -> bool`. Context: `{source: String, production: bool, discount: float}`; пустой context сохраняет прежнее поведение. Допустимые source: `manual`, `production`, `workshop`, `offline_workshop`; явная скидка `0 < discount <= 1`. Результат сохраняет прежние ключи, добавляет `ether_spent: int` и `mastery_awarded: int`; при отказе оба `0`.

- [ ] **Tests:** два последовательных запроса на последнюю пару → один успешный выход; `a == b` требует две единицы; не хватает эфира/одного входа → никакого частичного дебета или мастерства; неизвестная пара в production не тратится и не вызывает сеть; контекстная скидка одной линии не меняет цену следующей.

```gdscript
g._engine.inventory = {"fire": 2, "water": 2, "steam": 0}
g._engine.known_recipes = {g._pair_key("fire", "water"): true}
g._engine.ether = 12
g._engine.ether_overflow = 0
var result := g._engine._commit_brew("fire", "water", {
    "source": "workshop", "production": true, "discount": 0.9})
Selftest.check("workshop explicit discount", result["ether_spent"] == 11)
Selftest.check("workshop ordinary cost unchanged", g._engine._pair_cost("fire", "water") == 12)
```

- [ ] Подтвердить red; заменить чтение глобальной скидки явной только при наличии валидного context. Не округлять невалидную скидку в допустимую.
- [ ] Для production проверить известность рецепта, предел стека и реальные ресурсы до расхода. Сохранить manual fallback неизвестной пары и его существующий возврат/сетевой путь.
- [ ] Поставить короткий guard синхронного коммита до его побочных callbacks, освободить на каждой ветке возврата. Проверять guard в командах покупки оборудования и подтверждении сигила; не удерживать его через await/таймер/интервал линии.
- [ ] Не делать guard в `_spend_ether` блокирующим собственный внутренний расход коммита. Временная нехватка после ожидания ручного котла остаётся fail-closed.
- [ ] Проверить green, включая уже существующие проверки мьютекса, Аркана, эпохи Перегонки и текущие неудачные варки.

## Task 5: Хронологический офлайн, миграция и безопасная сводка

**Files:** scheduler, workshop, `main.gd`, `saves.gd`, `suite_workshop_offline.gd`, `suite_retort_return.gd` только новая сводка, fixture/selftest.

**Consumes:** Task 4 `advance` и статистика; текущие скорость/кап эфира, Родник, сохраняемая ручная `_craft_job`, безопасная запись сейва.

**Produces:** `WorkshopScheduler.replay_offline(from_ts: float, to_ts: float) -> Dictionary` с тем же итогом; `Saves._return_workshop: Dictionary`. Workshop экспорт дополнительно хранит дробные фазы линий, готовые кредиты и курсор, а не только абсолютную отметку.

## Зависимости и выполнение

Порядок: **1 → 2 → 3 → 4 → 5 → 6 → 7**. Полезные независимые части: таблица/валидация модели и контекст ядра; затем view и изолированные офлайн-сценарии при уже определённых интерфейсах. Не запускать одновременно редакторов одного `core.gd/main.gd/saves.gd`.

Рекомендуемый способ — ограниченные параллельные части реализации с интеграцией главным агентом: один исполнитель владеет моделью/балансом и их проверками, другой — исполнительным ядром/линиями и их проверками, общую проводку и проверки объединения делает главный агент. Следующие зависимые части стартуют после готовых интерфейсов, не на основе догадок. Никаких вложенных подагентов.

Более последовательный способ — выполнять вертикальные Tasks по одному, проверяя весь suite после каждого. Он снижает риск пересечения общих файлов, но обычно медленнее. При выборе любого способа исследования/ревью/прогоны интеграции не делегируются автоматически.

## Статус этого документа

Это **план**, не реализованное мастерство. В этой сессии изменена только документация. Последний PASS 939/939 относится к ранее выполненным багфиксам Аркана/Круга и не доказывает Tasks 1–7.

Известные ранее ограничения: runtime toast Lambda, импорт изображений, shutdown RID/resource warnings, временная нестабильность старого `u13 second hint in same frame spends nothing`, отсутствие подтверждённого нового Python/httpx. Незавершённая сигильная транзакция при перезапуске пока не сверяется; это отдельная задача, не скрытая гарантия нового scheduler.

Следующий gate: пользователь проверяет исполнимый план и подтверждает параллельное либо последовательное выполнение. После этого — failing behavior tests Task 1, а не заявления о готовности мастерства.
