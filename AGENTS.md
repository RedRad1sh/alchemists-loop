# Работа агентов

## Границы

- Работать в отдельном worktree `C:/Users/nkucherenko/agent-coding/wt/<name>` и своей ветке. Не выполнять git-операции в основном дереве пользователя.
- Не читать `.env*`, не изменять `addons/medusa`, сохранять `assets/decor`, `decor-samples` и `previews`.
- Коммиты только по явной команде пользователя; push, PR и merge требуют отдельного разрешения. Сообщения коммитов по-русски, без `feat:`/`fix:`; связанные изменения объединять.
- Спеки и планы хранить вне репозитория: `C:/Users/nkucherenko/agent-coding/docs/specs/` и `C:/Users/nkucherenko/agent-coding/docs/superpowers/plans/`.
- Отвечать кратко, по-русски, без эмодзи. Статус «только текстом» означает отсутствие запусков, записей и новых диспатчей.

## Портирование готовых модулей: A+B+C

- Не превращать перенос рабочей реализации в greenfield-разработку. Сначала переносить существующее поведение, менять только необходимые интеграционные границы.
- Батчить соседние задачи, меняющие одни файлы: один исполнитель, одна проверка батча. Не запускать несколько пишущих агентов одновременно; исполнителям не создавать вложенных агентов.
- Для малого фикса (ориентир: менее 60 изменённых строк, закрывающих конкретные findings) контроллер проверяет дифф сам, без отдельного повторного review-агента.
- UI-батчи контроллер проверяет сам по требованиям и диффу. Независимое ревью сохраняется для рискованной математики и один раз для всей готовой ветки.
- На батч планировать один поведенческий RED, один GREEN и проверку реального UI. Mutation-пробы — один раз на математическую подсистему, не на каждую UI-проверку. Дополнительные прогоны только для конкретного сбоя или изменённого поведения; не перегенерировать уже имеющиеся доказательства.
- Использовать точечный selftest для итераций, один полный прогон перед завершением. Не обходить изоляцию тестовых сейвов ради скорости.
- Godot запускать строго последовательно. Не запускать тяжёлые проверки параллельно. При неожиданном FAIL сначала проверять живые процессы и сигнатуру ошибки.
- Не тратить циклы на известный baseline-шум. Новые ошибки расследовать; предсуществующие фиксировать отдельно.
- Если UI-обвязка занимает больше часа, пересмотреть декомпозицию и цикл, а не добавлять новые гейты. Оценки времени не выдавать за измерения.

## Проверка результата

- Отчёт агента не является доказательством: проверять фактический дифф, тестовый вывод и полученные артефакты.
- Имя теста должно совпадать с проверяемым условием; тест обязан иметь сценарий, в котором он краснеет.
- UI проверять реальным запуском; приёмочные кадры открывать перед показом. Визуальное решение «оставить/браковать» принимает пользователь.
- Не стирать невыкоммиченные изменения через `git restore`, `checkout --` или `reset --hard`. Для временных проб сначала сделать копию и измерить хэш, восстановить из этой копии.
- Прогресс исполнения вести в ledger текущего плана; после восстановления контекста не повторять закрытые задачи. Противоречия плана разрешать против спеки, записывая конкретное решение.
